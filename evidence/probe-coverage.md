# Probe coverage — what each capability's recorded probe actually asserts

Generated by `python scripts/verify-probe-coverage.py` on 2026-10-03, against
`manifests/capabilities.json` at 27 capabilities. The script exits 0 whatever it finds: this is a
measurement, and a red build would be a claim it cannot support.

## The question

`scripts/assert-probes.py` re-runs each capability's recorded probe and compares strings. Its own OK
verdict says, in its own words:

> NOT a claim that the instrument ran: this entry declares no `probe.produces`, so this checker
> matched STRINGS only, and a stub which prints them satisfies it.

So for how many capabilities is that verdict hollow? A process that prints the recorded string and
exits 0 satisfies every comparison a strings-only checker makes. The answer, measured: **24 of 27**.
For **6** of those 24 it is worse than hollow — the checker never executes the probe at all.

## Ranking criterion, printed so it can be disagreed with

Weakness score, higher = worse, summed from named parts. Ties break on `id`, so the order is
deterministic, and every term is printed per row in the script's output.

| term | penalty | why |
| --- | --- | --- |
| base grade | D 400 · E 350 · C 300 · B 200 · A 100 | the four grades the brief defines, plus E (below) |
| the harness never executes this probe | +100 | it is in `assert-probes.py`'s `SKIP` set, or its `probe.command` is empty or prose, so none of its recorded strings are compared by anything, ever |
| no executable `negative_control.command` | +50 | the control is a declared plan, not a runnable refusal |
| not evidence-bound | +20 | no `run_log` + `sha256` pair, so `state: observed` rests on a summary line rather than a retained artifact |
| state is not `observed` | +10 | the entry is not claiming to have worked in the first place |

The `SKIP` set is **imported** from `assert-probes.py` rather than retyped. A second hand-typed copy
would drift and then be wrong in the exact direction that makes a table look better than the station
is. If that import fails the script prints a narrower definition instead of quietly reporting it.

**Evidence-bound** uses the derivation `doc-facts.py` already owns: a capability is bound when its
probe names **both** a `run_log` file and a `sha256` for it. Counting
`evidence_binding.status == "unverified"` instead would return 3, because that status key also sits
on a `planned` entry — a different question, and `doc-facts.py` records that difference on purpose.

**Grade E is a fifth label this script had to add, and it is not one of the brief's four.** The four
grades are not total over the eight possible `(exit, substring, artifact)` combinations: an entry
declaring `expect_exit` and `produces` but no `expect` falls through all four. The brief's own
negative test produces exactly that cell. Folding it into D would say such an entry "expects
neither", which is false — it expects an exit code. Folding it into C would say it expects a
substring, also false. It is counted and ranked separately rather than mislabelled. A reader who
prefers E merged into D can change one table in `scripts/verify-probe-coverage.py`. **No entry in
today's registry is grade E**, so the label is currently cosmetic on live data and load-bearing only
in the mutation sweep below.

**Every one of the 27 declares both `expect_exit` and `expect`.** That is why C and D are empty: the
registry is not lax about declaring expectations, it is uniform about it. Uniformity is exactly the
shape that hides a gap, because no entry looks like an exception.

The distribution that matters is therefore 3 A vs 24 B, and the single question of A over B is the
`probe.produces` artifact. The three A entries are `net.pcap.analyse`
(`%TEMP%\net-reverse-lab\pcaps\corpus.json`), `native.ghidra.decompile`
(`%TEMP%\gh-regress-good\summary.json`) and `fuzz.differential.parse` (`fuzz-lab/out/last-run.json`).

**24 of 27 hollow verdicts.** For those 24, `assert-probes.py` prints the STRINGS-ONLY OK text, which

## What a D-grade probe would have to assert

None today. For the record, and without speculating about anyone's intent, grade D means the entry
declares no `expect_exit` **and** no `expect`; a probe that landed there would assert nothing at
all about the run. For such an entry the minimum that makes the run falsifiable — as opposed to
present — is an exit code and a substring that the instrument's failure would change. Concretely,
asserting something like `expect_exit: 0` plus a `probe.expect` naming the instrument's own success
token would move it to grade B, and adding a `probe.produces` path for bytes the run must write would
move it to A. `assert-probes.py` already enforces exactly this shape: its `check()` emits
`CONTROL: declares no expect_exit, so nothing states what the refusal looks like` when a control
omits it, and its `--require-produces` mode reports `STRINGS ONLY` for every entry that declares no
artifact.

## Negative test, actually run

Five copies of the registry under `%TEMP%`, one A-grade entry (`net.pcap.analyse`) mutated per case.
`manifests/capabilities.json` was not edited; `git status --porcelain manifests/` is empty after the
sweep.

```
baseline        dropped=[]                          -> net.pcap.analyse grade=A  A=3 B=24 C=0 D=0 E=0  exit=0
drop-expect     dropped=['expect']                  -> net.pcap.analyse grade=E  A=2 B=24 C=0 D=0 E=1  exit=0
drop-exit       dropped=['expect_exit']             -> net.pcap.analyse grade=C  A=2 B=24 C=1 D=0 E=0  exit=0
drop-produces   dropped=['produces']                -> net.pcap.analyse grade=B  A=2 B=25 C=0 D=0 E=0  exit=0
drop-all-three  dropped=['expect','expect_exit','produces'] -> net.pcap.analyse grade=D  A=2 B=24 C=0 D=1 E=0  exit=0
```

Each of the three declared components is load-bearing: delete `expect` and the grade falls A→E;
delete `expect_exit` and it falls A→C; delete `produces` and it falls A→B; delete all three and it
reaches D. Every case exits 0, which is the contract — a measurement must not go red because the
registry is weak.

## 0. The technique that found all of it: ablation

Six of the seven findings in this document exist because one method was applied: **delete
the mechanism, require the existing suite to go red.** A suite that stays green after you
remove a component proves the component is untested, not that it is correct.

The primary source, quoted in `w1-agentworkflow.md~~:64-76~~`:

> **Source:** `anthropics/skills` — `skills/claude-api/shared/evals/eval-audit.md` §5,
> "Can it detect the change you're after?" (raw at
> `https://raw.githubusercontent.com/anthropics/skills/main/skills/claude-api/shared/evals/eval-audit.md`),
> cited `w1-agentworkflow.md~~:64-69~~`:
> *"The mechanism is wired. Whatever the score is supposed to depend on — a tool, a memory
> store, an instruction file — disable it and confirm the score drops; enable it and confirm
> it engages in the transcripts. If the score barely moves either way, the eval isn't
> measuring the lever you plan to pull."*
>
> **Corroboration:** `anthropic.com/engineering/harness-design-long-running-apps`, cited
> `w1-agentworkflow.md~~:70-73~~`: *"every component in a harness encodes an assumption about
> what the model can't do on its own, and those assumptions are worth stress testing, both
> because they may be incorrect, and because they can quickly go stale as models improve."*
>
> **Restated as a rule** (`w1-agentworkflow.md~~:75-76~~`): for each component, remove it and
> require the existing test suite to turn red.

The suite applies the same bar to the *validator*'s rules: a rule is load-bearing only if a
selftest case points at it. `w1-agentworkflow.md~~:919-921~~` records the driver and its result:
10 of 11 rule functions went red under ablation; **`r_shape` stayed green.**

**Why this document leads with the method and not the findings.** Every defect below is a
statement about a component that the estate already described as enforced. Reading would
not have found most of them — `gate.ps1`'s selftest printed `GATE SELFTEST OK: 10
refusals and grants all behaved.` (`w1-gateredteam.md~~:38~~`) while a grant forged from
nothing passed with `exit=0` (`w1-gateredteam.md~~:101~~`). Only mutation separates "the code
is right" from "nothing checks the code."

## 5. The validator: a tautology, two half-tested rules — and the one capability that arrived

### 5.1 R8 cannot fire — for any of its five effects

`w1-gateredteam.md~~:537-556~~`. `registry-verify.py` is the only other place `reach` is read,
and its check is self-cancelling:

```python
for eff in EFFECTS:
    if reach.get(eff): implied.append(eff)      # only implied if ALREADY declared
missing = [e for e in set(implied) if not reach.get(e)]   # so it is always declared
```

Measured, per effect (`w1-gateredteam.md~~:547-553~~`): remove `reach.proc_spawn` →
`R8 mentions it? NO`. Same for `exec_target`, `db_write`, `fs_write`, `net`. **All five are
unreachable via the mechanism that is supposed to enforce them.** The only way R8 fires is
through `requires` — `net == "any"` or `admin is True` — which is a different rule (R6)
doing the work.

**The two that matter most for the attach question, `proc_spawn` and `exec_target`, are
exactly the two that could never fire.** And the registry's own entry is the proof the
check is needed: `dynamic.device.frida` declares `exec_target`, `admin: true`, and a note
reading *"Frida injects into a running process … the effect is real even while the
capability is absent"* (`w1-gateredteam.md~~:561-564~~`). The registry knows; R8 cannot check.

**What else would also have produced the same result:** a rule that was never pointed at by
a selftest case. Which is exactly §5.3.

**After — the tautology is gone, measured 2026-10-02 by the reconciliation pass.** The
finding above is **superseded in the tree but not withdrawn from the record**: it is how
the defect was found, and §0's own rule is that a reader who cannot see the before-state
cannot tell a fix from a deletion. `r8_reach_must_be_declared`
(`scripts/registry-verify.py:238`) no longer builds `implied` from `reach`. Its own
docstring now records the defect in the first person:

> *"The previous version built `implied` by iterating EFFECTS and appending every effect
> `reach` already declared, then computed `missing = [e for e in implied if not
> reach.get(e)]`. Every member was therefore implied only when already present, so `missing`

### 5.5 `dynamic.win.frida` — registered, measured, and it does **not** claim interception

This is the one substantive new capability in the 2026-10-02 tree, and it is here rather
than in `dynamic-pairings.md` because **its most important property is a refusal**.
Full treatment in `dynamic-pairings.md` §1–§2; the registry entry is
`manifests/capabilities.json`, `id: dynamic.win.frida`.

**What it proves** (`state: observed`, one probe, one negative control):

- Frida **17.17.0** is installed on this station and can spawn-gate and inject into a
  **self-built** Windows PE — `Spawned … Resuming main thread!`, `Process terminated`,
  exit 0, against `c01-stringobf.exe` sha256 `2d59a3c5…`.
- The runtime image base is **not** the PE `ImageBase`, and it **moves every run**:
  `0x7ff6732f0000`, `0x7ff6d22d0000`, `0x7ff642d00000`, `0x7ff7c3a30000` across four runs
  of one binary, against `ImageBase 0x140000000` with `DllCharacteristics 0x8160`
  (`DYNAMICBASE=True`). This host ASLRs.
- A **module export** resolves to a live address inside the target
 (`Module.getGlobalExportByName('printf') = 0x7ffcf0e5d280`) — the one address source that
  needs no static analysis.
- `module_base + RVA` lands on real, attachable code: `base+0x1080` was accepted by
  `Interceptor.attach` with no error.
- **A symbol name does not resolve.** `DebugSymbol.fromName('main')` returned **0** on
  this statically linked MSVC binary, *in the same script and the same run* where the
  export name resolved fine.

**What it explicitly does NOT prove, and this is the part worth reading:**

> **THAT ANY INTERCEPTION HAPPENED.** The probe attaches an `Interceptor` and **no `onEnter`
> callback fired**, and this entry does not claim it did. Measured reason: on Windows the
> `frida -f` CLI **resumes the main thread BEFORE the injected script is loaded** — the
> target's own `usage:` line appears ahead of the first line of the script, and a companion
> hook on `ExitProcess` did not fire either. Interception *was* measured separately, through
> the Python API ordering `spawn → attach → create_script → load → resume`, where `onEnter`
> did fire and wrote a witness file naming the same address. **That ordering is not the
> command registered here, so it is recorded and not claimed.**

This is the estate's own standard applied to itself. `dynamic-pairings.md` §1.2 has a
transcript in which `HIT main via module-relative offset` *did* print — and the registered
probe does not reproduce it, because the CLI's resume-then-load ordering loses the race. A
capability entry that quoted the survey's transcript and shipped the CLI command would be
claiming a result its own runnable command does not produce.

**The negative control is the strongest thing in the entry.** It does *not* use a bogus
address; `0xDEADBEEF` would fault too, but it cannot distinguish *"you failed to rebase"*
from *"any bad address faults"*. It hands over the **genuine** static VA `0x140001080`
(`ImageBase 0x140000000` + RVA `0x1080`, and IDA recovers `main` there with size `0x17e`),
which is unmapped for exactly one reason — `DYNAMICBASE` moved the image. Measured stable
at `exit 1` with `Error: access violation accessing 0x140001080` over four consecutive runs,
while the probe one command earlier attached cleanly at `base+0x1080`.

**`frida-ps -ai` was rejected as a control because it HANGS for 300 s** on this device-less
host rather than refusing. **A hang is not a refusal**, so it is deliberately neither the
probe nor the negative control — and `does_not_prove` says exactly that.

**Why the `DebugSymbol.fromName('main') → 0` measurement is a boundary and not a style
preference:** a hook address on this class of target **must be an RVA plus the runtime
module base** — never a symbol name, and never the static VA. The negative control is what
makes that distinction measured rather than pedantic, and it is why the fifth typed edge
(§6) exists: `dynamic.win.frida` consumes `native.ida.list_functions`'s
`native.func.addr` as an **RVA source and nothing more**, rebasing it against
`runtime.module.base`.

**Update 2026-10-02, commit `96e718c` — the gap above was then CLOSED, by a sibling entry
rather than by an edit.** `dynamic.win.frida.intercept` is registered, `state: observed`,
with a real probe (`native-lab/tools/frida_spawn_gate.py`, `verdict=INTERCEPT-PROVEN`) that
uses the ordering the CLI cannot: `spawn(suspended) → load → resume → HIT`. It publishes
`runtime.hook.hit` as a *produced fact* — **HIT at `0x7ff79e0115d0`, tid 44248, hit count 1**
— and, more importantly, `instrument.ordering` as a produced fact, so the ordering is
readable off the output instead of inferred from a tool's internals.

**`dynamic.win.frida` was NOT edited.** Its `composition_note` states why, and the sentence
is the rule this document argues for:

> *"WHY A SIBLING RATHER THAN AN EDIT. Editing `dynamic.win.frida` to claim interception
> would make the entry describe something its registered probe does not do. The charter's
> rule is that a capability states what its probe proves; **a capability whose probe cannot
> show the claim is a claim wearing a capability's clothes.**"*
>
> — `manifests/capabilities.json`, `dynamic.win.frida.intercept.composition_note`
>
**What this changes about §5.5's conclusion.** §5.5 said the refusal was the deliverable.
That was true when written and it was **incomplete**: a refusal names the gap; a refusal

## 9. Registry-driven routing — the fix that replaced a hardcoded table

**This section did not exist when the review was written.** It is here because the routing
defect — `mission.ps1` selecting from a hardcoded 7-key `$QUESTION_TYPES` hashtable while
`question_types` was declared on every capability and read by nothing — was the largest
open item in `composition-plan.md`, and it is now closed. Two earlier references to "§10"
in this document meant this section and were left pointing at a number that did not exist;
they are corrected to §9.

### 9.1 What replaced it

`Get-Route` (`scripts/mission.ps1:215`) derives the route from the registry. Its docstring
is its specification, and it names **six rules in a fixed order**: state, question type,
unproducible-required-input, hard-edge closure (iterated to a fixpoint), unmet-hard-edge,
and no-producer-pulled-in-for-a-refinement. Each rule carries an `# ABLATE-ANCHOR` comment
so the ablation driver can neutralise exactly that rule — `state-filter` `:279`,
`unproduced-input` `:285`, `question-type-filter` `:295`, `edge-closure` `:328`,
`unmet-hard-edge` `:350`, `argv-slot` `:459`.

Ordering is now derivable rather than typed: a capability runs **after** whatever produces
a fact its `invoke.argv` binds, and every remaining tie breaks on the capability's index in
the registry's own `capabilities` array, which travels on every step as `registry_index`. A
cycle among declared edges is broken at that index and reported in `cycles`, never looped
on. The docstring is explicit that an unexplainable tie-break is its own kind of silent
behaviour — which is the correct standard to hold a reimplementation to.

### 9.2 Q5 and Q6 now refuse with exit 2, and that is the whole point

Before: `-Action Plan -QuestionType Q6.crypto` printed `plan 0 step(s)` and **exited 0**.
`Get-RouteRefusal` (`:492`) exists to make that impossible, and it has two distinct arms —
(a) the registry routes nothing, (b) the registry routes something and not one step is
invocable under this grant. Merging them is what produced "0 steps, exit 0", because the
two have different fixes. The entry point refuses at `:672-674` *before* the mint, so an
unservable mission never gets a grant written for it, and again at `:751-755` *after* the
plan is on disk, so the artifact the operator needs survives the refusal.

**Measured by me, 2026-10-02, from the repo root:**


`Q5.vuln-shape` behaves identically (`fuzz.differential.parse skipped_no_invoke`,
`{"ok":false,"exit":2}`; re-run unpiped so `$?` is the mission's exit code and not the

**The refusal names the capability and the reason**, which is the difference between a
refusal and an error: *"crypto.jose.parse [skipped_not_in_grant]: inside the registry, and
outside this grant"* is something the operator can act on. `plan 0 step(s)` + exit 0 was
not.

## 10. The one sentence

Every fix in the 2026-09-30 audit was applied to the *data* the gate reads and none to the
*code that reads it* (`w1-gateredteam.md~~:674-680~~`). The parent closed that gap: the
identity is now sealed with DPAPI, the grant has a field allow-list, `state` filters what
is mintable, the registry's digest is bound into the seal so a one-byte registry edit
invalidates every outstanding grant, `mission.ps1` routes from the registry instead of a
hardcoded table, and the seven verdict gates are each proven load-bearing by an ablation
that goes red when it is removed.

**What remains open, named rather than dropped.** Two of the three items this document
originally carried as open are now closed in the tree and proved (§5.1 R8, §5.3 the three
uncovered rule branches). What survives is:

2. **The six-mutation LYING-CLEAN fixture has not been re-run** against the current

   suite is green and the registry binding is measured, but G4–G10/G-FS are the parent's

Each is a control that passes for the wrong reason, or a claim not re-measured — the
